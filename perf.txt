--------------------------------------------------------------------------------
1. ROOT CAUSE — the pipeline was decode-bound, not YOLO-bound
--------------------------------------------------------------------------------
First full run on DJI_0033 (grab-through sampling, the historical default):

  [timing] DJI_0033.MP4: loop=250.8s [decode=222.1s (89%), yolo=14.4s (119 frames,
           121ms/f), other=14.2s] 14 dets | segmentation=5.6s csv=0.00s tracks=2

  * YOLO inference was only ~14 s. DECODE was 222 s — 89% of the loop.
  * Why: iter_sampled_frames() advances an OpenCV VideoCapture by grab()-ing through
    EVERY frame to move forward, then retrieve()s only the ~1-in-N it samples. On a
    long-GOP 10-bit 5.3K HEVC stream, grab() still software-decodes almost every
    frame. Over the ~154 s of "empty water" the adaptive stride skips, it decoded
    ~4600 frames it immediately discarded.
  * Detection itself is cheap and correct: the only shark is at ~1:07-1:14
    (two tracks, 01:09 peak 0.86 / 6.1 ft and 01:10 peak 0.79 / 6.9 ft).

Conclusion: to go faster we must stop DECODING frames we never look at — not
optimize YOLO.


--------------------------------------------------------------------------------
2. DECODE STRATEGY BENCHMARKS (60 s span of DJI_0033)
--------------------------------------------------------------------------------
2a. OpenCV-only options (what we could do without a new dependency):

  grab-through (current, software)        66.7 s   30 samples   baseline
  grab-through + CAP_PROP_HW_ACCELERATION 63.5 s               ~5%  (readback kills it)
  seek by CAP_PROP_POS_MSEC               48.7 s               ~27% faster
  seek by CAP_PROP_POS_FRAMES             55.6 s               ~18% faster

  Findings:
  - OpenCV's HW-acceleration flag barely helped: it still returns a full
    5472x3078 10-bit CPU array, so the GPU->CPU readback eats the win.
  - OpenCV seeking only saved ~27%: its FFMPEG backend seeks to the prior keyframe
    then DECODES FORWARD to the exact frame. OpenCV cannot decode keyframes-only.

2b. ffmpeg CLI, decode-only (-f null), same 60 s span:

  full software decode                    63.2 s   1x
  full HW (videotoolbox)                  22.2 s   2.8x
  keyframe-only (-skip_frame nokey)       12.7 s   5x
  keyframe-only + HW (videotoolbox)        1.6 s   ~39x   *** but see caveat ***

  Caveat: through a rawvideo->numpy PIPE, -skip_frame nokey still emitted duplicated
  frames unless -fps_mode passthrough was set, and -skip_frame + -hwaccel did NOT
  compose cleanly. So the ffmpeg CLI could not deliver the 39x into numpy. Also, an
  ffmpeg subprocess needs the ffmpeg BINARY present — the frozen app does not ship
  one (OpenCV's internal libav != the CLI). => chose PyAV instead.

2c. PyAV (libav in-process), decode + to_ndarray(bgr24), 60 s span:

  SW full                        218.9 s  (122 ms/f, 1799 frames)   1x
  HW videotoolbox full            37.6 s  (21 ms/f)                 5.8x
  SW keyframe-only                12.3 s  (205 ms/f, 60 frames)     18x
  HW videotoolbox + keyframe-only  1.94 s (32 ms/f, 60 frames)    113x

  KEY RESULT: in PyAV, VideoToolbox HW decode COMPOSES with skip_frame='NONKEY'
  (keyframe-only) — the exact combination the ffmpeg CLI pipe could not do. This is
  the lever the whole optimization rests on. PyAV also needs no external binary
  (bundles libav), so it survives PyInstaller freezing.

3. THE IMPLEMENTATION — keyframe-scan sampling (src/keyframe_sampling.py)
--------------------------------------------------------------------------------
Two-mode sampler matching iter_sampled_frames()'s generator protocol exactly
(yields (idx, bgr_frame), receives had_detection via send(), returns the same stats
dict), so all [timing]/[stats]/[timeline] logging keeps working:

  * SCAN mode (empty water): skip_frame='NONKEY' -> decode ONLY keyframes.
    One decoded frame per GOP (~1 s here) instead of grab-through's 30. This is
    actually FINER cadence than the old accelerated stride (which reached 2 s), so
    recall improves while decode collapses.
  * DENSE mode (a shark is visible): on the first detection, seek to that keyframe
    and decode forward at stride 10, until 3 consecutive samples are empty, then
    return to scanning past the window.
  * VideoToolbox HW decode auto-selected via _pick_hwaccel() (videotoolbox -> cuda
    -> d3d11va/dxva2/vaapi -> software), with allow_software_fallback=True.

Safety / no-regression design:
  * try_keyframe_sampler(path, logger) is the single entry point. It honors the
    SHARKEYE_KEYFRAME_SAMPLING env flag, eagerly opens the container and decodes one
    probe keyframe, and returns None on ANY problem — so every call site
    transparently falls back to the old grab-through path. It never raises.
  * PyAV import is guarded at every call site: if `av` is unavailable the app still
    runs on grab-through.
  * DEFAULT IS OFF (opt-in via SHARKEYE_KEYFRAME_SAMPLING=1). Kept opt-in until a
    full video is driven through the FROZEN bundle (startup already verified, below).

Wired into all three decode paths:
  - VideoProcessingWorker.run()      (GUI, live preview)      src/sharkeye_app.py
  - the in-app headless run()         (no preview)             src/sharkeye_app.py
  - HeadlessVideoProcessor.run()      (CLI batch)              src/headless_prediction.py
In keyframe mode the cv2 capture is no longer advanced, so per-detection timestamps
come from frame_num/fps (exact for CFR) instead of CAP_PROP_POS_MSEC.

4. HISTORIC PERFORMANCE — full-pipeline runs on DJI_0033 (real YOLO, GUI harness)
--------------------------------------------------------------------------------
All runs found the SAME two tracks (01:09 and 01:10), same confidences, same
lengths (6.0-6.1 ft / 6.9 ft), 14 detections — i.e. no recall/quality regression.

  Path                       loop      decode          yolo    realtime  wall clock
  -----------------------    -------   -------------   ------   --------  ----------
  grab-through (original)    250.8s    222.1s (89%)    14.4s     0.8x      4m17s
  SW keyframe-scan           107.2s     71.2s (66%)    13.0s     1.8x      1m53s
  HW + keyframe-scan          44.2s     10.7s (24%)    11.2s     4.4x      50s

  Net: 250.8s -> 44.2s  = 5.7x faster loop
       222.1s -> 10.7s  = 20x less decode

Standalone full-model bench (grab-through vs SW keyframe, no Qt):
  grab-through 210.5s (decode 200.7s/95%)  ->  SW keyframe 83.2s (decode 71.5s) = 2.5x

New bottleneck after the fix: decode is now the SMALLEST phase (24%). "other"
(~22 s: live-preview color-convert/emit + tracking + progress) is now the largest
phase. That is the next optimization target if more speed is wanted (e.g. skip the
preview downscale/emit in headless, or throttle it harder).


--------------------------------------------------------------------------------
5. FROZEN-APP (PyInstaller) VALIDATION
--------------------------------------------------------------------------------
`av` added to requirements.txt; SharkEye.spec collects av submodules + its libav
dylibs. Built bundle (dist/SharkEye.app, ~1.2 GB) contains BOTH libav builds:
  cv2  -> libavcodec 61 / libavutil 59   (cv2/__dot__dylibs/)
  PyAV -> libavcodec 62 / libavutil 60   (av/__dot__dylibs/)
Different MAJOR versions => the dynamic linker loads them as distinct libraries;
no symbol clash. The only symptom is a cosmetic objc warning at startup:
  "Class AVFFrameReceiver is implemented in both ... libavdevice.61 ... and ...
   libavdevice.62 ..." (from libavdevice, which we don't use).

Smoke test (frozen app, QT offscreen, keyframe flag on): launched clean through
"Using device: mps" -> "Model warmup complete" -> "SAM warmup complete" ->
"Models ready", stayed alive, no crash. This exercises the cv2+PyAV dual-libav
IMPORT coexistence in the bundle (startup imports both).

RESIDUAL GAP before flipping the default ON: drive a full video through the BUILT
app so keyframe DECODE (not just import) is exercised inside the frozen bundle. The
harness that does this is not bundled, so this was validated in dev only.
